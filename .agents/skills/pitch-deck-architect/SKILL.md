# Pitch Deck Architect

Build a persuasive, evidence-grounded narrative with conclusion-driven titles and visual slides. Keep detailed explanation in conversational speaker notes rather than crowding the screen.

## 1. Establish the presentation brief

Identify the audience, decision or takeaway, presentation duration, required format, project stage, and available evidence. Use supplied context and artifacts first; ask only for missing information that materially changes the deck. Honor an explicit slide count, institutional rubric, or user-provided structure over defaults.

For project pitches and defenses, distinguish implemented capabilities, measured results, proposed features, and external dependencies. Never invent users, market size, revenue, benchmarks, citations, or successful test results. Mark unresolved facts as placeholders or omit unsupported claims.

## 2. Shape an 8-10 slide core story

Default to 8-10 main slides, with Q&A backups outside that count. Adapt the order to the audience. A useful sequence is:

1. The main conclusion and why the audience should care.
2. The specific user problem and its consequence.
3. Evidence of the need and the intended users.
4. The proposed solution and its distinguishing benefit.
5. The key user journey or product demonstration.
6. The architecture or method that enables the result.
7. Validation, measured outcomes, and the limits of the evidence.
8. Alternatives, trade-offs, and differentiation.
9. Remaining risks, next milestones, or implementation plan.
10. The concrete ask or defense conclusion.

Merge or remove beats to fit the requested count and time. In a technical defense, emphasize methodology, design decisions, evaluation, and limitations. In a pitch, emphasize the problem, value, evidence, viability, and ask. Do not force unsupported business content into an academic defense.

## 3. Write visual slides

Use action titles that state a conclusion, such as “Offline drafts survive a lost connection,” rather than topic labels such as “Offline features.” Ensure the title is supported by the evidence on that slide.

Keep each main slide under 20 visible words, counting its title, captions, and labels. Move detailed citations, qualification, and explanation to speaker notes or backup slides; preserve readable source attribution where necessary. If a mandated template requires more visible detail, acknowledge the exception and prioritize clarity over artificial omissions.

Give each slide one visual argument: a workflow, architecture diagram, annotated screenshot, comparison, chart, or other purposeful visual. Use real source material and meaningful labels. Avoid decorative imagery that competes with the point, dense paragraphs, and screenshot collages with unreadable text.

## 4. Write conversational speaker scripts

For each slide, provide:

- The conclusion-driven title and under-20-word screen copy.
- The visual composition or actual visual asset, depending on the requested deliverable.
- A speaker script that explains the claim, evidence, and implication in natural spoken language.
- A transition to the next point and an estimated duration.

Keep notes speakable, avoid reading the slide verbatim, and distinguish established results from future plans. Fit the total script to the allocated presentation time, leaving room for pauses and the demo. Do not treat an outline or image preview as a finished editable deck when an actual deck file was requested.

## 5. Choreograph a 90-second demo

Default to this timing when the user requests a short live demo:

| Time | Purpose |
| --- | --- |
| 0-10 seconds | State the user's goal and starting state |
| 10-25 seconds | Show the primary entry point and essential input |
| 25-50 seconds | Complete the core workflow |
| 50-70 seconds | Demonstrate one relevant exception or recovery |
| 70-85 seconds | Show the saved result and evidence of success |
| 85-90 seconds | Connect the result to the presentation's conclusion |

Provide exact actions, expected visible results, narration, and a fallback screenshot or recording plan. Rehearse only authorized actions using synthetic or approved data. If a capability does not work, adapt the demo and state its limit rather than simulating a successful live result. Avoid relying on unstable network or unprepared credentials for the critical moment.

## 6. Prepare Q&A backups

Add focused backups for likely questions about architecture, method, security, performance, evaluation, alternatives, limitations, cost, or next steps as relevant to the audience. Give each backup a direct answer, supporting evidence, and a short spoken response. Keep them visually readable; detailed technical references can exceed the main-slide word budget when needed.

## 7. Verify the deliverable

Check the main slide count, visible word budget, narrative consistency, total timing, claim provenance, readable charts, and demonstration prerequisites. For an actual presentation file, use the available presentation-authoring workflow, render or preview every slide, and check for clipped text, overlap, font problems, and unreadable visuals. Report unverified claims and demo dependencies. Deliver the requested deck or outline together with scripts, demo flow, and backups as appropriate; do not publish or send it to others without authorization.
